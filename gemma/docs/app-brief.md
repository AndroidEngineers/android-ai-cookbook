# PocketStories — Gemma on Android

Status: Building. The user selected PocketStories next and then refined it into a camera-driven offline adventure. See README and verification for the implemented first slice; model/device compatibility remains unverified.

## Current product decision (supersedes the original text-first scope below)

Show everyday objects to a vision-capable Gemma model, generate a short fictional scene, choose/type the next direction, and optionally add a shake-triggered spark suggestion. Camera snapshots are deliberate, never continuous recording. Model setup, camera/photo input, story drafts and bookshelf are the first slice. Editable discoveries, inventory, branches, PDF export and narration are subsequent milestones. The original text-only Gemma 3 1B candidate is not appropriate for camera understanding; the current candidate is Gemma 4 E2B GPU with LiteRT-LM 0.16.1, still pending device inference verification.

The following original brief is retained as planning background; implemented scope is listed above and in README.

## Learning promise

An Android engineer can explain and implement the complete path from a compatible Gemma model file to an offline, streamed story in a lifecycle-safe Compose app. Explain model weights versus inference runtime versus app policy, not just a library call.

Project: `gemma/`; application ID: `com.androidengineers.pocketstories`.
Audience: Kotlin/Compose developers familiar with coroutines. Include the necessary LiteRT-LM foundation here; completing PocketBench is not a prerequisite.

## Product and MVP

A personal story studio: choose a character, setting, and tone, generate a short scene locally, type what happens next, and keep a story on your bookshelf.

1. Model setup: supported artifact instructions, local import, validation, storage information, removal and recovery.
2. New story: character, setting and tone with bounded input; no complicated prompt editor required.
3. Reader: streamed scene, Stop, retry, accept or discard a draft, and a user-authored next direction.
4. Story continuity: bounded context assembled from accepted story facts and recent accepted scenes.
5. Bookshelf: Room-backed stories, resume, rename and delete.

Later: integrated resumable downloads, branching timelines, generated illustrations, narration, multiple models and summarization-based context compression. No Firebase, cloud generation, training or fine-tuning in the MVP. No silent cloud fallback. Runtime inference needs no Gemini API key; obtaining gated weights may separately require a provider account and acceptance of model terms. Do not embed access tokens or redistribute weights without checking terms.

## Design direction

Warm cream reading canvas, plum accents, book-cover cards, clear chapter typography; matching dark mode. Four destinations: Bookshelf, New Story, Reader, Model Setup. Model status is visible but technical controls stay in setup. Show a calm generation indicator and an obvious Stop action. Use bundled original/licensed cover art; do not imply illustrations are generated by the text model.

Include missing/importing/invalid/loading/ready/generating/stopping/unavailable states, empty bookshelf, partial draft and interrupted-session recovery. Support large text, TalkBack, rotation, compact/expanded windows and edge-to-edge layouts.

## Technical direction and first feasibility gate

Use the official LiteRT-LM Kotlin API as the candidate runtime. Start by evaluating a small instruction-tuned Gemma artifact listed as compatible by the runtime, with Gemma 3 1B as an initial candidate rather than a locked selection. Compare a larger mobile-oriented Gemma only if the target device and story quality justify it.

Before UI implementation, record a tested tuple: model source/revision/hash/format/quantization, runtime version, Android SDK/ABI, device/OS/RAM, backend, model size and storage headroom. Pin exact dependencies; never use dynamic versions. Run real text generation, stream, stop, release/reload and airplane-mode generation. Verify native cancellation semantics instead of assuming cancelling a Flow stops inference. Test CPU/GPU only where supported; NPU is not an MVP requirement. If feasibility fails, record the result and revise the model/runtime before building the product around it.

First acquisition path: one-tap in-app HTTPS download with progress, cancellation, resumable private staging, storage checks, pinned size/SHA-256 verification and atomic promotion. Manual document-picker import remains under Advanced setup. Keep the app open; after process death the next explicit download resumes the saved partial file. No scheduled background service is implemented.

## Architecture and ownership

Compose → screen ViewModel → StoryRepository → StoryGenerator adapter → LiteRT-LM.
ModelRepository owns artifact metadata/import/removal; Room owns story content and draft states. Use constructor injection and one app module initially. Add interfaces at the inference/storage test boundaries, not a generic universal AI manager.

A single runtime owner serializes load, generation, cancellation and unloading. Initialize native resources off the main thread. Use one active generation and scoped conversations; close conversations before the engine. Rotation must not create another engine or generation. Explicit app-background handling cancels generation and releases resources when safe; process restart restores text, not native handles or KV cache. Reconstruct model input from saved app data.

Persist accepted scenes and a separate partial draft. Retry replaces a pending draft, not accepted history. Context includes the story specification, user-reviewed facts and recent accepted scenes with an explicit budget and output reserve. Explain that persisted chapters and runtime context are different. Surface omissions; do not claim perfect long-story memory. Quantization, model weight size and peak RAM are different quantities; RAM checks are advisory, not proof of compatibility.

## Acceptance and verification

- Fresh documented setup produces a real scene on a named physical device; generation still works in airplane mode after setup.
- Stop is verified to cease native work; late chunks cannot alter a replacement attempt.
- Concurrent taps cannot load multiple engines; unsupported/corrupt files fail clearly.
- Rotation, backgrounding and restart recover saved stories without silently restarting generation.
- Context excludes rejected/unfinished drafts and preserves the latest accepted story state.
- Import interruption, insufficient storage, model deletion while in use and load failure have explicit recovery. Do not deliberately crash a user's device to test OOM.
- Unit tests cover context selection, draft transitions, retry isolation, import state and repository persistence. Fake generation is clearly separate from real-model evidence.
- Physical-device report measures cold/warm load, time to first text, generation rate where measurable, memory and repeated-session thermal behavior. No universal speed or battery claims.
- Evaluate a fixed story prompt set for continuity, instruction following, repetition, abrupt endings and undesirable output; include failures and model settings. Local inference is not a safety filter or encryption guarantee. Document Android backup/export behavior and avoid prompt logging.
- Build debug/release, unit tests, lint, UI failure/main-flow checks and release native packaging/shrinking verification.
